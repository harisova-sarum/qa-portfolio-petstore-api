# Тест-кейсы: Swagger Petstore API

Формат: ID | Метод и endpoint | Тип | Ожидаемый результат

---

## Pet

| ID | Запрос | Тип | Ожидаемый результат |
|---|---|---|---|
| API-01 | POST /pet | Позитивный | 200, тело ответа содержит переданные данные (имя, статус), id сохранён для дальнейших запросов |
| API-02 | GET /pet/{petId} (существующий id) | Позитивный | 200, id в ответе совпадает с запрошенным, время ответа < 2 сек |
| API-03 | GET /pet/{petId} (несуществующий id, например 999999999) | Негативный | 404 |
| API-04 | GET /pet/{petId} (нечисловой id, например "abc") | Негативный | 400 или 404, без серверной ошибки 5xx |
| API-05 | PUT /pet (обновление статуса) | Позитивный | 200, поле status в ответе обновлено |
| API-06 | GET /pet/findByStatus?status=available | Позитивный | 200, ответ — массив, все элементы имеют статус available |
| API-07 | GET /pet/findByStatus?status=<некорректное значение> | Негативный | Код ответа < 500 (без падения сервера) |
| API-08 | DELETE /pet/{petId} | Позитивный | 200 |
| API-09 | GET /pet/{petId} после удаления | Негативный | 404 — подтверждение, что питомец действительно удалён |

## Store

|---|---|---|---|
| API-10 | GET /store/inventory | Позитивный | 200, тело ответа — объект с количеством питомцев по статусам |

## User

|---|---|---|---|

## Примечания

- Petstore.swagger.io — публичный демо-стенд без строгой валидации на бэкенде (в частности, может принимать некорректные значения без ошибки) — это учитывается в негативных тест-кейсах: проверяется отсутствие серверных ошибок 5xx, а не строгая валидация, которой на этом стенде может не быть.
- Тест-кейсы API-02–API-09 образуют сквозной сценарий на одном и том же питомце (id передаётся через переменную коллекции), что демонстрирует зависимые сценарии тестирования, а не только изолированные запросы.
- API-03 (несуществующий id): на практике id `999999999` оказался занят другим пользователем публичного стенда — сервер вернул существующего питомца с кодом 200 вместо ожидаемых 404. Это подтверждает риск, описанный в примечаниях: на shared-стенде "случайно выбранный" id не гарантированно свободен. Более надёжный способ проверить поведение 404 — использовать id, который мы только что удалили сами (см. API-09)

## Находки в ходе выполнения (не отражённые в исходных тест-кейсах)
- **API-10** (инвентарь): реальный ответ содержит множество нестандартных статусов, накопленных от других пользователей публичного стенда (опечатки — "avalible", "availabl"; разный регистр — "Available"/"available"; мусорные значения — "string", "5000", "Busy", "invalid_status"). Подтверждает отсутствие серверной валидации поля status — тот же паттерн, что и в API-07.
- **API-12** (некорректное количество): API принимает отрицательное значение quantity (-5) без ошибки валидации, код 200. Демонстрирует отсутствие бизнес-валидации входных данных на этом демо-стенде.
- **API-17** (неверный пароль): обнаружена находка безопасности — API возвращает код 200 и сообщение "logged in", идентичное успешному логину, даже при заведомо неверном пароле. Пароль фактически не проверяется сервером. Существующая проверка (только "код < 500") этого не выявляла. Рекомендация для доработки: усилить тест — явно проверять, что ответ на неверный пароль НЕ содержит "logged in".
- Заказы (**Store**) создаются успешно даже с petId уже удалённого питомца — сущности Pet и Store не связаны валидацией на уровне API.
